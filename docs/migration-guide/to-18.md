# Migrating to 18.0.0

This release contains significant or breaking changes.

We've made our rules check values more accurately, including those that use custom properties, and replaced dependencies with Node.js built-ins and smaller packages to improve supply chain security.

## Significant changes

We've:

- fixed `declaration-property-value-no-unknown` false negatives for values containing custom properties
- added `declaration-property-custom-property-allowed-list` and `value-type-custom-property-required-list` rules
- added `value-no-invalid` rule

### Fixed `declaration-property-value-no-unknown` false negatives for values containing custom properties

We've fixed [`declaration-property-value-no-unknown`](../../lib/rules/declaration-property-value-no-unknown/README.md) false negatives for values containing custom properties by substituting their declared values for `var()` functions before checking the declaration value.

For example, `var(--foo)` is now flagged, as `red` is unknown to the `top` property:

```css
:root {
  --foo: red;
}

a {
  top: var(--foo);
}
```

For custom properties registered with `@property`, the rule substitutes only the declared values that match the registered syntax, or a value of the syntax when none do. Given:

```css
@property --foo {
  syntax: "<color>";
}

a {
  --foo: 1px;
  top: var(--foo);
}
```

- `1px` is flagged, as `--foo` is registered as `<color>`
- `var(--foo)` is now flagged, as `<color>` values are unknown to the `top` property

The problem message for the former now says what the custom property is registered as, e.g. `Unknown value "1px" for property "--foo", registered as "<color>"`, and passes the syntax as a fourth [message argument](../user-guide/configure.md#message).

You can use the [`referenceFiles`](../user-guide/configure.md#referencefiles) configuration property to include custom properties declared in separate files:

```diff json
{
  "extends": ["stylelint-config-standard"],
+ "referenceFiles": "tokens/*.css"
}
```

### Added `declaration-property-custom-property-allowed-list` and `value-type-custom-property-required-list` rules

We've added the [`declaration-property-custom-property-allowed-list`](../../lib/rules/declaration-property-custom-property-allowed-list/README.md) rule to specify which custom properties are allowed in which properties, and the [`value-type-custom-property-required-list`](../../lib/rules/value-type-custom-property-required-list/README.md) rule to specify which value types require custom properties.

For example, to allow only `--spacing-*` custom properties in `margin` and `padding` properties and only `--radii-*` in `border-radius`, and to require custom properties for `<length>` values:

```diff json
{
  "extends": ["stylelint-config-standard"],
  "rules": {
+   "declaration-property-custom-property-allowed-list": {
+     "/^(margin|padding)/": ["/^--spacing-/"],
+     "border-radius": ["/^--radii-/"]
+   },
+   "value-type-custom-property-required-list": ["length"]
  }
}
```

Given:

```css
a {
  border-radius: var(--spacing-m);
  margin: 1rem;
}
```

- `--spacing-m` is flagged by [`declaration-property-custom-property-allowed-list`](../../lib/rules/declaration-property-custom-property-allowed-list/README.md), as only `--radii-*` custom properties are allowed in `border-radius`
- `1rem` is flagged by [`value-type-custom-property-required-list`](../../lib/rules/value-type-custom-property-required-list/README.md), as custom properties are required for `<length>` values

The [customizing guide](../user-guide/customize.md#enforce-conventions) has a fuller example that uses a tokens file.

### Added `value-no-invalid` rule

We've added the [`value-no-invalid`](../../lib/rules/value-no-invalid/README.md) rule. It flags values that cannot be parsed and math expressions that add or subtract a number to a dimension or percentage, for example:

```css
a {
  top: calc(1px + 2);
}
```

The [`declaration-property-value-no-unknown`](../../lib/rules/declaration-property-value-no-unknown/README.md) rule previously made these checks. See [the breaking change below](#changed-declaration-property-value-no-unknown-to-no-longer-report-invalid-values).

We've turned the rule on in the latest version of the [standard config](https://www.npmjs.com/package/stylelint-config-standard), along with four other rules that help you [avoid errors](../user-guide/rules.md#avoid-errors):

- [`at-charset-rule-no-invalid`](../../lib/rules/at-charset-rule-no-invalid/README.md)
- [`selector-no-deprecated`](../../lib/rules/selector-no-deprecated/README.md)
- [`selector-no-invalid`](../../lib/rules/selector-no-invalid/README.md)
- [`selector-no-unmatchable`](../../lib/rules/selector-no-unmatchable/README.md)

## Breaking changes

We've removed:

- support for end-of-life and older versions of Node.js
- `context.fix` property
- support for CommonJS-style filename-less and extension-less locator paths
- `declaration-block-single-line-max-declarations` rule
- `*syntax` options from `declaration-property-value-no-unknown`
- resolution of packages from the global `node_modules` directory

And changed:

- the CLI to parse arguments with `node:util.parseArgs`
- `globbyOptions` to support only a subset of options
- `declaration-property-value-no-unknown` to no longer report invalid values
- TypeScript config files to be loaded by Node.js's built-in type stripping
- color detection to use new `color` option with `node:util.styleText`
- hyperlink detection

### Removed support for end-of-life and older versions of Node.js

We've removed support for Node.js versions less than 22.22.2, 24.15.0 and 26.0.0, including end-of-life 20.x, 23.x and 25.x, to update all our dependencies.

We recommend updating to the latest version of Node.js.

### Removed `context.fix` property

We've removed the `context.fix` property that we [deprecated in 16.8.2](../../CHANGELOG.md#1682---2024-08-15).

You should update your plugin(s) to pass a `fix` callback to the [`report` utility](../developer-guide/plugins.md#stylelintutilsreport) instead, which handles [configuration comments](../user-guide/ignore-code.md#parts-of-a-file) for you:

```diff js
root.walkRules((ruleNode) => {
  const { selector } = ruleNode;

  if (!selector.includes("foo")) return;

- if (context.fix) {
-   ruleNode.selector = selector.replace("foo", "bar");
-
-   return;
- }
-
  report({
    result,
    ruleName,
    message: messages.rejected(selector),
    node: ruleNode,
+   fix: () => {
+     ruleNode.selector = selector.replace("foo", "bar");
+   }
  });
});
```

And set `meta.fixable` to `true` on the rule:

```diff js
const meta = {
  url: /* .. */,
+ fixable: true,
};
```

### Removed support for CommonJS-style filename-less and extension-less locator paths

We've removed support for CommonJS-style filename-less and extension-less paths in locators, such as `extends` and `plugins`, to align with ESM import behaviour.

You should update your config to use full paths:

```diff js
export default {
- extends: ["./", "stylelint-config-foo/bar"],
- plugins: ["./plugin"],
+ extends: ["./index.js", "stylelint-config-foo/bar.js"],
+ plugins: ["./plugin.js"],
};
```

And when using our [Jest preset](https://www.npmjs.com/package/jest-preset-stylelint) to test your plugin(s):

```diff js
-global.testRule = getTestRule({ plugins: ["./"] });
+global.testRule = getTestRule({ plugins: ["./index.js"] });
```

### Removed `declaration-block-single-line-max-declarations` rule

We've removed the `declaration-block-single-line-max-declarations` rule, which we overlooked when we [removed the stylistic rules in 16.0.0](./to-16.md#removed-deprecated-stylistic-rules).

You should remove the rule from your configuration object, or use the [`@stylistic/declaration-block-single-line-max-declarations`](https://stylelint-stylistic.github.io/rules/declaration-block-single-line-max-declarations) rule of the community [`@stylistic/stylelint-plugin`](https://www.npmjs.com/package/@stylistic/stylelint-plugin) instead:

```diff json
 {
+  "plugins": ["@stylistic/stylelint-plugin"],
   "rules": {
-    "declaration-block-single-line-max-declarations": 1
+    "@stylistic/declaration-block-single-line-max-declarations": 1
   }
 }
```

### Removed `*syntax` options from `declaration-property-value-no-unknown`

We've removed the `propertiesSyntax` and `typesSyntax` options from [`declaration-property-value-no-unknown`](../../lib/rules/declaration-property-value-no-unknown/README.md) that we [deprecated in 17.5.0](../../CHANGELOG.md#1750---2026-03-19).

You should update your config to use the shared and more performant [`languageOptions`](../user-guide/configure.md#languageoptions) configuration property instead:

```diff json
{
+ "languageOptions": {
+   "syntax": {
+     "properties": { "top": "| <--foo()>" },
+     "types": { "--foo()": "--foo( <length-percentage> )" }
+   }
+ },
  "rules": {
    "declaration-property-value-no-unknown": [
      true,
-     {
-       "propertiesSyntax": { "top": "| <--foo()>" },
-       "typesSyntax": { "--foo()": "--foo( <length-percentage> )" }
-     }
    ]
  }
}
```

### Removed resolution of packages from the global `node_modules` directory

We've removed the fallback that resolved `extends` and `plugins` packages from npm's global `node_modules` directory, to rely on Node.js's module resolution instead.

You should install the packages your config uses locally, as the Node.js documentation [strongly encourages](https://nodejs.org/api/modules.html#loading-from-the-global-folders):

```shell
npm install --save-dev stylelint stylelint-config-standard
```

If you share one config across projects, two workarounds remain, though we don't recommend either:

- keep the config file and its `node_modules` in an ancestor directory, such as your home directory, as Stylelint currently searches upwards for a config file
- resolve the packages from npm's global root in your config file:

```js
// stylelint.config.mjs
import { execSync } from "node:child_process";
import path from "node:path";

const globalRoot = execSync("npm root -g", { encoding: "utf8" }).trim();

export default {
  extends: [path.join(globalRoot, "stylelint-config-standard")]
};
```

### Changed the CLI to parse arguments with `node:util.parseArgs`

We've changed the CLI to parse arguments with [`node:util.parseArgs`](https://nodejs.org/api/util.html#utilparseargsconfig), which accepts fewer spellings of flags.

If you separate the value of `--fix` with a space, you should attach it with `=` instead, as the CLI now reads the value as a file path:

```diff shell
-stylelint "**/*.css" --fix lax
+stylelint "**/*.css" --fix=lax
```

The CLI reports the following changes as invalid options and names the flag to use instead.

If you use an alias of a long flag, you should use the flag itself:

```diff shell
-stylelint "**/*.css" --aei --mw 0
+stylelint "**/*.css" --allow-empty-input --max-warnings 0
```

| Alias    | Flag                                |
| -------- | ----------------------------------- |
| `--aei`  | `--allow-empty-input`               |
| `--cei`  | `--compute-edit-info`               |
| `--di`   | `--disable-default-ignores`         |
| `--go`   | `--globby-options`                  |
| `--id`   | `--ignore-disables`                 |
| `--ip`   | `--ignore-pattern`                  |
| `--mw`   | `--max-warnings`                    |
| `--rd`   | `--report-needless-disables`        |
| `--rdd`  | `--report-descriptionless-disables` |
| `--risd` | `--report-invalid-scope-disables`   |
| `--rud`  | `--report-unscoped-disables`        |

If you use camelCase flags, you should update them to their kebab-case names:

```diff shell
-stylelint "**/*.css" --ignorePath .gitignore --allowEmptyInput
+stylelint "**/*.css" --ignore-path .gitignore --allow-empty-input
```

If you give a boolean flag a value with `=`, you should use the flag or its `--no-` form:

```diff shell
-stylelint "**/*.css" --cache=false
+stylelint "**/*.css" --no-cache
```

If you attach the value of a short flag with `=`, you should separate it with a space:

```diff shell
-stylelint "**/*.css" -c=stylelint.config.mjs
+stylelint "**/*.css" -c stylelint.config.mjs
```

### Changed `globbyOptions` to support only a subset of options

We've replaced [globby](https://github.com/sindresorhus/globby) with [tinyglobby](https://github.com/SuperchupuDev/tinyglobby) to reduce our transitive dependencies. As a result, the `globbyOptions` option and its `--globby-options` flag now support only the options that behave the same with tinyglobby:

- `braceExpansion`
- `caseSensitiveMatch`
- `dot`
- `extglob`
- `followSymbolicLinks`
- `ignore`

If you used other options, you should replace them:

- `cwd` with the top-level [`cwd`](../user-guide/node-api.md#cwd) option, which relative globs are now resolved from
- `gitignore` with the [`ignorePath`](../user-guide/options.md#ignorepath) option ([`--ignore-path`](../user-guide/cli.md#--ignore-path) on the CLI) pointing at your `.gitignore` file

For example:

```diff shell
-stylelint "**/*.css" --globby-options '{"gitignore":true}'
+stylelint "**/*.css" --ignore-path .gitignore
```

Unlike globby's `gitignore` option, the `ignorePath` option:

- reads only the files you name, not `.gitignore` files in subdirectories or parent directories
- resolves patterns relative to `cwd`, not to the directory of the `.gitignore` file
- replaces the default `.stylelintignore` lookup, so you should also name your `.stylelintignore` file if you use one, e.g. `--ignore-path .gitignore --ignore-path .stylelintignore`

Other options, such as `deep` and `expandDirectories`, no longer have an equivalent.

We may migrate to the Node.js built-in glob API, such as [`node:fs.glob`](https://nodejs.org/api/fs.html#fsglobpattern-options-callback) and [`node:path.matchesGlob`](https://nodejs.org/api/path.html#pathmatchesglobpath-pattern), in the future. We recommend using globs that are compatible with it: name dot directories, e.g. `".storybook/**/*.css"`, instead of using the `dot` option, and wrap special characters in square brackets, e.g. `"[[]foo[]]/**/*.css"`, instead of escaping them with backslashes.

### Changed `declaration-property-value-no-unknown` to no longer report invalid values

We've moved the checks for values that cannot be parsed and for invalid math expressions from [`declaration-property-value-no-unknown`](../../lib/rules/declaration-property-value-no-unknown/README.md) to the new [`value-no-invalid`](../../lib/rules/value-no-invalid/README.md) rule, as neither depends on the property.

If you don't extend the [standard config](https://www.npmjs.com/package/stylelint-config-standard), you should turn on the new rule to keep reporting these problems:

```diff json
{
  "rules": {
    "declaration-property-value-no-unknown": true,
+   "value-no-invalid": true
  }
}
```

### Changed TypeScript config files to be loaded by Node.js's built-in type stripping

We've changed TypeScript config files, such as `stylelint.config.ts`, to be loaded by Node.js's [type stripping](https://nodejs.org/api/typescript.html#type-stripping) rather than the `typescript` package, which you no longer need to install.

Only erasable syntax is supported. You should update your config to:

- use `import type` for type-only imports
- replace syntax that needs transforming, such as `enum` and `namespace`

For example:

```diff ts
-import { Config } from "stylelint";
+import type { Config } from "stylelint";
```

### Changed color detection to use new `color` option with `node:util.styleText`

We've changed our built-in formatters to use the new [`color`](../user-guide/options.md#color) option to force color on or off, rather than looking for `--color` and `--no-color` in the process arguments.

The `--color` and `--no-color` CLI flags are unchanged.

If you use the Node.js API with the `string` or `verbose` formatter and relied on `--color` or `--no-color` in your process arguments, you should pass the `color` option instead:

```diff js
const { report } = await stylelint.lint({
  files: "**/*.css",
  formatter: "string",
+ color: false,
});
```

We've also replaced [picocolors](https://github.com/alexeyraspopov/picocolors) with [`node:util.styleText`](https://nodejs.org/api/util.html#utilstyletextformat-text-options) to reduce our dependencies. When the `color` option isn't set, `FORCE_COLOR` takes precedence over `NO_COLOR`, and colors are off when the `NODE_DISABLE_COLORS` environment variable is set or `FORCE_COLOR` is `0`.

If you want color in your CI logs, you should use the `--color` flag or set the `FORCE_COLOR` environment variable:

```diff shell
-stylelint "**/*.css"
+stylelint "**/*.css" --color
```

The `color` option and its flags take precedence over all these environment variables.

### Changed hyperlink detection

We've changed hyperlink detection to no longer depend on color, the `FORCE_HYPERLINK` environment variable or a list of terminals known to support hyperlinks.

The `string` and `verbose` formatters now add hyperlinks in any terminal except in CI or on Windows outside Windows Terminal.
